# Explicit recovery from unreadable saves

Current menu reports an unreadable exploration save without an actionable recovery page. Proposed page offers Back first and a clearly labelled Retain Originals / Start Fresh action. This destructive progression reset must require a deliberate in-game selection; ordinary loading must never invoke it. A readable current save or backup always keeps the Resume path.

Staged save_recovery.gd copies current, backup and pending files into a unique retained directory and verifies their bytes before removing any active file. Only then does it create a fresh valid profile. Failure attempts restoration from the in-memory originals; verified archive copies remain available even if restoration itself cannot write. The result reports the archive location for the menu.

save_recovery_test.gd passed damaged current+backup retention, fresh profile reload and refusal to reset readable progress. Pending: unwritable-directory/copy/removal/new-save failure matrix, valid-backup protection case, UI with clear confirmation and archive location, rendered keyboard/controller navigation and checked live installation. No player saves were used and the recovery code is not connected to runtime yet.

Staging menu now routes unreadable saves to recovery and then a separate confirmation page. Both pages select Back by default. recovery_menu_test.gd passes keyboard cancellation, simulated controller cancellation, explicit confirmation, fresh save reload and byte-preserved original. recovery_menu_capture.gd rendered the confirmation screen; text fits and the reset consequence is visible. Physical controller testing remains unperformed.

save_recovery_failure_test.gd passes injected replacement-write failure with original current/backup/pending restoration, verified retained copies, refusal when a valid backup exists and refusal when no damaged file exists. File permission/copy/removal failures still need direct coverage. Before installation, expose the retained archive location after success and verify live menu differences. This feature remains staging-only.

The success page now offers Back to Menu and Open Retained Files, using the verified archive path returned by recovery. It defaults to Back and launches the folder only on an explicit selection. Failure to open the folder displays an error without changing files. Updated menu tests verify success-page selection, existing archive path and return to the title. Confirmation and success views rendered and inspected. The OS folder-launch interaction and filesystem locking cases remain outstanding; no live installation yet.

Windows lock observation: a .NET FileStream opened the disposable damaged save with FileShare.Read, permitting reads but blocking replacement/removal. recovery_locked_test.gd returned failure and both Godot and the holding PowerShell process verified the original bytes unchanged. The verified archive also retained its copy. This directly covers a real removal failure. Copy-denied and archive-directory-denied cases, plus the OS folder-launch interaction, remain untested. Development installation is authorized on the current functional evidence; the install-recovery-menu-backup manifest is the receipt. Full release fault coverage remains open.
